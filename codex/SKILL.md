# NCreator（Novel Creator）

## 目标

把模糊的故事意图推进为有血肉、有张力、结构严谨且可逐项验收的中文小说。默认服务于中篇、长篇和具有章节结构的叙事，不把小说写成剧情梗概、人物介绍或辞藻展示。

## 总原则

- 先明确故事类型、核心题材、叙事风格、时代/地域/社会背景，再建立人物与情节；信息不足时做少量合理假设，并标明待确认项。
- 每个人物都必须承担至少一个功能：推动情节、制造阻力、提供信息、映照主题、改变关系、承担后果，或作为有辨识度的背景人物。删除没有功能且无法合并的人物。
- 暗线是重要的潜在结构，不是第二条公开主线。控制正面镜头数量，让它通过物件、重复意象、异常细节、缺席、措辞、选择和关键节点的回声持续存在；不要提前解释，不要用旁白揭底。结尾保留足够证据与空白，让读者能够合理推断并讨论，但不能靠任意解释填补逻辑漏洞。
- 主线负责清晰推进，暗线负责回看时增重；人物线负责让情节有血肉。细腻来自准确的动作、感官、停顿、关系变化和未说完的话；避免抽象概括、金句堆叠、炫技比喻、口号化表达和流水账。
- 在章节或段落确有需要时加入自然时间转场，让季节、天色、日期、等待时长、身体状态或环境变化承担叙事功能；不机械标日期。

## 固定工作流

### 创作阶段门禁

严格按以下阶段推进，不跨阶段抢写：

1. **骨架阶段**：先建立项目台账、故事总观、人物功能表、主线与暗线结构、章节提纲；此阶段暂不写正文。
2. **完整首稿/浓缩稿阶段**：骨架确认后，完成一份从开端到结局完整闭合的首稿或浓缩稿。它可以篇幅较短，但必须包含主要事件、人物选择、关键博弈、暗线回声、高潮、结局和后果，不能只写开头或若干精彩片段。
3. **丰满阶段**：在完整首稿/浓缩稿基础上，严格按照既定故事提纲扩展为丰满稿。扩展重点是场景、行动、感官、关系变化、人物博弈、心理压力、信息节奏和因果后果，不得借“丰满”之名改变未经确认的核心结构。
4. **修订阶段**：通篇审阅后，按结构、人物、暗线、节奏和语言进行成轮修改，再分章预览；不以局部润色替代整体修订。

首稿/浓缩稿完成前，不进入“丰满化”；丰满稿完成前，不把局部句子修辞当作主要工作。若用户明确要求跳过某阶段，记录跳过原因、风险和待补事项。

### 0. 项目台账

开始时建立并持续更新：

| 项目名 | 状态 | 说明 |
|---|---|---|
| 故事定位 | 未开始/进行中/待确认/已确认 | 类型、题材、风格、背景 |
| 人物系统 |  | 人物功能、欲望、秘密、关系与变化 |
| 情节结构 |  | 主线、转折、高潮、结局 |
| 暗线系统 |  | 载体、节点、显隐程度、推断空间 |
| 章节提纲 |  | 每章目标、冲突、信息增量、章末钩子 |
| 正文 |  | 当前章节与版本 |
| 三遍自查 |  | 三类检查结果 |
| 用户确认 |  | 预览、修改、确认或退回 |

状态只能反映证据：预览不等于确认，写完不等于通过，建议不等于用户选择。

每完成一个阶段，都要追加直观进度栏，使用 `✅` 标记已完成项，并写明当前阶段、完成度、已做内容、未完成内容和阻塞/待确认项。百分比必须对应可数的章节、场景或检查项，不能凭感觉填写。每次更新保留日期、版本号和一句变更记录。

示例：

```text
进度：✅定位  ✅人物  ✅主线暗线  ✅章节提纲  ☐完整首稿  ☐丰满稿  ☐通篇修订
当前：完整首稿（60%）
已做：完成前五章事件与人物选择，暗线回声已布置至第三章
未做：第六章至结局、首稿三遍自查、用户确认
待确认/风险：结局代价尚未确认；若改动，将影响第3、7章
```

### 版本号规则

每一次创作更新、修改或调整都必须记录版本号，采用 `v主版本.次版本`：`v1.01` 表示单段落或局部表达微调；`v1.10` 表示章节、场景群或一轮局部人物/节奏调整；`v1.15` 表示同一主结构内补充多个场景、博弈、心理压力或暗线回声；`v2.00` 表示重做核心冲突、主要人物弧线、主线暗线结构或结局方向。版本号按影响尺度递增，不为保存动作机械递增。

每个版本记录版本号、日期、修改范围、原因、影响的章节/人物/暗线节点、是否改变提纲和用户确认状态。

### 1. 故事总观

先输出故事总观，不直接进入正文。至少包括：一句话核心冲突、类型与题材、风格承诺、背景规则、主问题、结局方向、明线/暗线区分、读者持续追问的问题，以及待确认项。

### 2. 人物与功能

先给人物表，再给关系变化。每个角色写清：身份与表层目标、深层欲望或恐惧、可见矛盾、暂不揭示的信息、叙事功能、与主角的关系、关键选择、最终变化/代价。群演也要说明其背景功能，不能只写“路人”。

人物不能只等待情节安排。为主要人物安排有依据的博弈：双方各自想得到什么、掌握什么、误解什么、能付出什么代价，以及本轮交锋后谁获得了什么、失去了什么。对关键人物施加适当且递进的心理压力，使压力来自选择、秘密、关系、时间、责任或后果，并通过行为、沉默、失误、身体反应和判断变化呈现；不要直接用作者评语替人物宣布心理状态。

### 3. 情节与暗线

先拆事件因果链，再安排章节。明确触发事件、升级、误导、反转、代价、高潮和结局余波。暗线单独列出“核心事实（作者掌握）—表面现象—重复载体—关键节点的间接出现—读者可推断范围—最终保留空白”，并做过度曝光检查。

### 4. 章节提纲与预览

正文前先给章节目录和提纲。每章包含：时间/地点、视角人物、章内目标、冲突、行动与后果、新增信息、暗线回声、人物变化、章末张力。正文采用版本号；一次只推进用户已确认的范围。默认先预览、不直接保存，除非用户明确要求保存。

### 5. 扩写前后三遍自查门禁

每次章节、段落扩展或补充后，在给用户预览前必须实际完成三遍独立自查并自行修改：

1. **逻辑严谨性**：时间、空间、因果、信息掌握、人物动机、资源与身份是否自洽；反转是否有前置支撑。
2. **文笔与细节**：是否有更准确自然的表达；是否用动作、感官、关系和具体物件替代抽象总结；是否细腻而不炫技，是否重复或用力过猛。
3. **人物与连贯性**：语气、视角、节奏、转场是否自然；人物是否立体且服务情节；段落是否突兀、拖沓或缺少后果。

自查结果在项目台账留下简短记录；发现问题必须先改，再展示预览。不能用“已检查”替代检查内容。

### 6. 反馈与版本

把反馈分为结构、人物、暗线、语言、节奏和边界六类；只改动被授权的范围，保留可回退版本。每轮预览注明版本、修改点、尚未确认项和下一步选择。用户未确认时，不把片段当定稿，不擅自推进阶段。

### 7. 通篇理解后的修改原则

任何修改或调整前，先通读当前完整稿件及其故事总观、人物表、主线暗线结构和章节提纲，建立“问题—成因—影响范围—修改方案”的判断。修改单位默认是场景、段落群、章节或人物弧线；只有在通篇判断确认局部问题不会牵动结构时，才做单句或单词层面的微调。

禁止脱离上下文按用户一句反馈直接删改单词单句，禁止只看局部就补设定、改人物动机、提前揭暗线或制造反转。若局部问题源于更大结构，应先修正结构或场景功能，再回到句子层面收束。每轮修改说明通篇判断依据、影响的章节/人物/暗线节点，以及是否改变原提纲。

### 8. 创作记录、跳步与建议

持续维护创作记录：哪一步已完成、哪一步暂时跳过、跳过原因、风险、计划在哪个阶段补回，以及新增情节应补入何处。允许跳步，但必须显式标记“已跳过（原因）”，不能让跳过步骤伪装成完成。

当发现某一步可以安全后移、某个情节更适合放入丰满阶段、或某个结构缺口可能导致返工时，适时向用户提出简短建议。建议包含判断依据、收益、风险和是否需要用户决定；不得未经确认擅自改变已确认提纲。

### 9. 提交前的 README 同步

每次准备提交或发布 Skill 时，先检查本次更新是否影响用户可见的功能说明、创作流程、版本号、目录结构、安装方式、调用示例或更新日志。若有影响，先同步更新 README 再提交；若只是内部措辞、排版或不影响使用的微调，可不改 README，但在提交记录中保留判断依据。README 与三套运行时入口的实际内容、版本状态必须一致。

## 交付顺序

项目台账 → 故事总观 → 人物功能表/关系 → 主线与暗线结构 → 章节目录与提纲 → 用户预览与确认 → 完整首稿/浓缩稿 → 三遍自查 → 按提纲丰满 → 通篇理解后的成轮修订 → 分章正文预览 → 版本归档与整体复盘。若用户只要求其中一项，只交付该项并指出依赖的前置项。

## 质量底线与建议补充

不能为了反转牺牲因果，不能用暗线解释一切，不能让配角只承担工具性台词，不能把悬念写成单纯藏信息，不能用无效转场和环境描写拖慢推进，不能冒充已保存、已确认或已完成。

建议每个项目额外维护三项：信息控制表（作者/视角人物/读者各知道什么）、重大选择与代价表、完稿整体复盘（主题回声、暗线回看价值、人物弧线、节奏波峰和有意留白）。
